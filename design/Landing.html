tsvector · GIN · ts_headline replaces elasticsearch

Full-text search that ranks, highlights, and indexes itself.

Titles and notes are tokenised into a tsvector column by a BEFORE INSERT/UPDATE trigger and indexed with GIN — so every write keeps the index hot without application-layer plumbing. Reads use SearchRank for relevance ordering and SearchHeadline to return the matching span with terms wrapped for the template to highlight.

  • English stemming and stop-words via the built-in dictionary
  • Ranking via ts_rank — no scoring code in Python
  • ts_headline returns the matched snippet, pre-marked
  • One GIN index. No second service to keep in sync.
todos/views.py PY 
from django.contrib.postgres.search import (
    SearchQuery, SearchRank, SearchHeadline,
)

def search_todos(request):
    q = request.GET.get("q", "")
    query = SearchQuery(q)

    todos = (
        Todo.objects
            .annotate(
                rank=SearchRank("search_vector", query),
                headline=SearchHeadline("title", query),
            )
            .filter(search_vector=query)   # GIN index lookup
            .order_by("-rank")
    )
    return render(request, "todos/search_results.html",
                  {"todos": todos, "q": q})
pg_notify · LISTEN · channels replaces redis pub/sub

Live cross-tab updates fired straight from a write trigger.

Every insert and update on todos_todo calls pg_notify with the row as JSON. A Django Channels consumer opens a long-lived asyncpg listener on the todo_updates channel and forwards each payload over a WebSocket. No Redis channel layer, no broker — the database is the bus.

  • Trigger runs AFTER INSERT OR UPDATE — guaranteed write order
  • ASGI worker (Daphne) holds one persistent listener per connection
  • Open two tabs, write in one, see it in the other in <50ms locally
  • Fine for single-node deploys; for fan-out across replicas, use a broker
todos/triggers.sql  ·  todos/consumers.py SQL · PY 
-- on every write, ship the row as JSON to listeners
CREATE OR REPLACE FUNCTION notify_todo_change() RETURNS trigger AS $$
BEGIN
  PERFORM pg_notify('todo_updates', row_to_json(NEW)::text);
  RETURN NEW;
END; $$ LANGUAGE plpgsql;

# asgi consumer — one async listener per socket
class TodoConsumer(AsyncWebsocketConsumer):
    async def connect(self):
        await self.accept()
        conn = await asyncpg.connect(DATABASE_URL)
        await conn.add_listener("todo_updates", self.on_notify)

    async def on_notify(self, _c, _pid, _ch, payload):
        await self.send(text_data=payload)
materialized view · concurrent refresh replaces redis cache

A self-refreshing dashboard with zero cache code.

Aggregated counts by status live in a MATERIALIZED VIEW with a unique index on status. An AFTER INSERT/UPDATE/DELETE trigger calls REFRESH MATERIALIZED VIEW CONCURRENTLY so readers never block, and the dashboard view is a one-line raw() query. There's no cache layer to invalidate because there isn't a cache layer.

  • Pre-computed aggregates — reads cost a constant O(rows-in-view)
  • CONCURRENTLY needs the unique index; trade write cost for read speed
  • Counts with FILTER (WHERE …) instead of N round-trips
  • Best for moderate write volumes — for heavy writes, switch to a debounced refresh
migrations/0003_todo_stats.sql SQL 
CREATE MATERIALIZED VIEW todo_stats AS
SELECT
  status,
  COUNT(*)                                  AS total,
  COUNT(*) FILTER (WHERE due_date < NOW()) AS overdue,
  COUNT(*) FILTER (WHERE status = 'done')  AS done
FROM todos_todo
GROUP BY status;

CREATE UNIQUE INDEX ON todo_stats(status);

-- refresh after every write, non-blocking for readers
CREATE OR REPLACE FUNCTION refresh_todo_stats() RETURNS trigger AS $$
BEGIN
  REFRESH MATERIALIZED VIEW CONCURRENTLY todo_stats;
  RETURN NULL;
END; $$ LANGUAGE plpgsql;
select for update · skip locked replaces sqs + celery

A concurrent job queue that fits in one SELECT.

When a todo is created, a trigger inserts a row into todos_job. A plain Python worker pulls jobs with SELECT … FOR UPDATE SKIP LOCKED — atomic, no double-processing — runs the work, and updates the row. Spin up three workers with docker compose up --scale worker=3 and they cooperate out of the box. The same pattern powers Oban and Que in production.

  • One SELECT claims a job and locks it for the txn — no race
  • Failed jobs flip to status='failed' for a retry sweep
  • pg_notify('job_queue', …) lets workers wake instantly instead of polling
  • Adds load to the primary; great until you're at queue-as-a-service scale
todos/worker.py PY 
def process_jobs():
    conn = psycopg2.connect(DATABASE_URL)
    while True:
        with conn.cursor() as cur:
            cur.execute("""
                SELECT id, todo_id, job_type, payload
                FROM   todos_job
                WHERE  status = 'queued'
                ORDER  BY created_at
                LIMIT  1
                FOR UPDATE SKIP LOCKED
            """)
            job = cur.fetchone()
            if job:
                try:
                    handle_job(job)
                    cur.execute("UPDATE todos_job SET status='done', "
                                "processed_at=NOW() WHERE id=%s", [job[0]])
                except Exception:
                    cur.execute("UPDATE todos_job SET status='failed' "
                                "WHERE id=%s", [job[0]])
                conn.commit()
        time.sleep(0.5)

04 · HONEST ABOUT THE LIMITS

A learning project, not a production architecture recommendation.

read before shipping
heads-up

Every pattern here has real limits at scale that the dedicated tools are designed to solve. For side projects, internal tools, and early-stage products these patterns can meaningfully cut infra. For high scale, use the right tool for the job.

Full-text search
good enough · most apps

Postgres FTS is genuinely strong for moderate volumes and simple ranking. It won't match Elasticsearch on faceted search, custom tokenisers, or distributed indexing across hundreds of millions of documents.

LISTEN / NOTIFY
single-node · no persistence

Works well at low-to-moderate event rates on one DB node. No fan-out across replicas, no message persistence — an offline consumer misses the notification. For guaranteed delivery, reach for a real broker.

Materialized views as cache
recompute cost · low-write

REFRESH … CONCURRENTLY is non-blocking but still a full recompute on every refresh. For dashboards with heavy aggregations and high write volume, the trigger cost adds up. Redis gives O(1) writes with explicit TTLs.

SKIP LOCKED queue
production-proven · in scope

Solid pattern used by Oban (Elixir) and Que (Ruby) in production. Caveat is shared load on your primary — at very high throughput you'll want a dedicated queue that doesn't compete with transactional traffic.
